# CLOCK DOMAIN CROSSING (CDC) ⭐⭐⭐⭐⭐

This is the natural continuation after metastability.

CDC is **very important for VLSI placements**, especially for questions involving asynchronous signals, synchronizers, FIFOs, and metastability.

---

# 1. What is Clock Domain Crossing?

**Clock Domain Crossing (CDC)** occurs when a signal transfers from one clock domain to another clock domain.

```text
Clock Domain A                 Clock Domain B
```

Clock A                       Clock B

```
  │                             │

  ↓                             ↓
```

Logic A ───── Signal ───────► Logic B

The two clocks may have:

* Different frequencies
* Different phases
* No fixed relationship

---

# 2. Placement Definition ⭐⭐⭐⭐⭐

> **Clock Domain Crossing is the transfer of a signal or data between two different clock domains.**

---

# 3. Why is CDC Dangerous?

Suppose:

```text
Clock A
```

↓

Logic A

↓

Signal

↓

Logic B

↑

Clock B

The signal generated by Clock A may change at any time relative to Clock B.

Therefore, the receiving flip-flop may sample the signal very close to its clock edge.

This can cause:

**Setup/Hold violation**

which can lead to:

**Metastability**

# 5. Common CDC Solutions ⭐⭐⭐⭐⭐

The solution depends on **what type of signal/data is crossing**.

### Single-bit control signal

**2-FF synchronizer**

### Pulse signal

Possible techniques:

* Pulse synchronizer
* Pulse stretching
* Toggle synchronizer
* Handshake

### Multi-bit data

Common solutions:

* Handshake
* Asynchronous FIFO
* Gray-code techniques

---

# 6. 2-FF Synchronizer

For a single-bit signal:

```text
Source Domain
```

```
 │

 │ Async signal

 ▼
```

┌────┐

│ FF1│

└────┘

```
  │

  ▼
```

┌────┐

│ FF2│

└────┘

```
  │

  ▼
```

Destination Logic

Both FF1 and FF2 use the **destination clock**.

Important:

**FF1 and FF2 are clocked by destination clock**

---

# 7. Why Does the 2-FF Synchronizer Work?

Suppose FF1 becomes metastable.

```text
Async signal
```

```
 ↓

FF1

 ↓
```

Metastability

```
 ↓
```

Resolution time

```
 ↓

FF2

 ↓
```

Stable signal

FF2 samples FF1 after approximately one destination-clock period.

This gives FF1 time to settle.

Therefore:

**Probability of metastability propagation decreases**

---

# 8. 🔥 Important Placement Trap

### Q.

Should FF1 and FF2 in a standard 2-FF synchronizer use different clocks?

❌ No.

Both use the:

**destination clock**

# 9. Single-Bit CDC Example

Suppose:

```text
Clock A = 50 MHz
```

Clock B = 100 MHz

A control signal is generated in Clock A and used in Clock B.

Because the clocks have different frequencies, the signal should not simply be connected directly to Clock B logic.

A typical solution:

```text
Clock A                    Clock B
```

Signal ───────────────► FF1 ───► FF2 ───► Logic

```
                       │        │

                       └────────┴── Clock B
```

---

# 10. Asynchronous vs Synchronous Clocks

### Synchronous clocks

There is a known timing relationship between them.

### Asynchronous clocks

There is no fixed phase/timing relationship.

For example:

```text
Clock A = 100 MHz
```

Clock B = 75 MHz

If their relationship is not controlled, they can be considered asynchronous for CDC purposes.

# 12. Multi-Bit CDC Problem ⭐⭐⭐⭐⭐

Suppose an 8-bit bus crosses clock domains:

```text
10101100
```

You might think:

```text
Bit 0 → FF
```

Bit 1 → FF

...

Bit 7 → FF

using independent synchronizers.

This is generally **not sufficient for coherent multi-bit data**.

Why?

Different bits may be captured at different times.

Example:

Old:

```text
00001111
```

New:

```text
11110000
```

The receiver might temporarily see a mixture such as:

```text
00110011
```

which was never a valid source value.

Therefore:

**Multi-bit CDC requires special techniques**

---

# 13. Handshake-Based CDC ⭐⭐⭐⭐

A handshake ensures that the receiver knows when data is valid.

Basic concept:

```text
Source                    Destination
```

Data ───────────────────────►

```
   │

   │ Request ───────────►

   │

   │ ◄──────── Acknowledge
```

Typical sequence:

1. Source places data.
2. Source sends request.
3. Destination receives request.
4. Destination captures data.
5. Destination sends acknowledgement.
6. Source knows transfer is complete.

---

# 14. Why Use Handshake?

Because the sender and receiver don't need to assume that the two clocks are aligned.

The handshake provides:

**Controlled data transfer**

---

# 15. Asynchronous FIFO ⭐⭐⭐⭐⭐

For continuous or high-throughput multi-bit data crossing between unrelated clocks, an **asynchronous FIFO** is a common solution.

```text
        Write Clock Domain
```

```
           │

           ▼

      ┌─────────┐
```

Data ───► │ Async   │ ───► Read Domain

```
      │  FIFO   │

      └─────────┘

           ▲

           │

      Read Clock
```

The FIFO provides separate:

* Write clock
* Read clock

---

# 16. Why is Gray Code Used in Async FIFO?

This is a common VLSI placement question.

Binary counters can have multiple bits change simultaneously.

Example:

```text
0111 → 1000
```

Four bits change.

If the bits cross asynchronously, the receiver could temporarily see an invalid combination.

Gray code changes only **one bit at a time**.

Example:

```text
Binary:
```

0111 → 1000

Multiple bits change

Gray:

0100 → 1100

One bit changes

Therefore:

**Gray code reduces ambiguity during CDC pointer synchronization**

---

# 17. CDC Technique Selection ⭐⭐⭐⭐⭐

| Signal Type                    | Common Solution                        |
| ------------------------------ | -------------------------------------- |
| Single-bit level               | 2-FF synchronizer                      |
| Single-bit pulse               | Pulse/toggle synchronizer or handshake |
| Multi-bit control/data         | Handshake                              |
| High-throughput multi-bit data | Asynchronous FIFO                      |
| FIFO pointer crossing          | Gray code                              |

---

# 18. Pulse Crossing Problem

Suppose a pulse is generated in a fast clock domain:

```text
Source:
```

****████****

If the destination clock is slower:

```text
Destination samples:
```

```
 ↑          ↑
```

The destination may completely miss the pulse.

Therefore, simply passing a short pulse through a 2-FF synchronizer may not guarantee that the pulse is detected.

Possible solutions include:

* Pulse stretching
* Toggle synchronizer
* Handshake

---

# 19. Toggle Synchronizer ⭐⭐⭐⭐

Instead of transferring a short pulse directly, the source toggles a bit.

For example:

```text
Initial = 0
```

Event 1 → 1

Event 2 → 0

Event 3 → 1

The destination synchronizes this toggle.

A change in the synchronized value indicates that an event occurred.

This is useful when:

**A pulse must cross between unrelated clock domains**

# 20. CDC Interview Question ⭐⭐⭐⭐⭐

### Q.

Why can't we directly connect a signal from one asynchronous clock domain to another?

### Answer:

Because the receiving flip-flop may sample the signal during a setup/hold window, causing metastability.

Therefore a suitable CDC technique must be used.

---

### Q.

What is the simplest CDC solution for a single-bit level signal?

**2-FF synchronizer**

---

# 22. Another Interview Question

### Q.

What is commonly used for multi-bit high-throughput data crossing unrelated clocks?

**Asynchronous FIFO**

---

# 23. Another Interview Question

### Q.

Why is Gray code used in asynchronous FIFOs?

Because only one bit changes between adjacent Gray-code values, reducing the chance of an inconsistent pointer value when the pointer crosses clock domains.

**One-bit transition**

---

# 24. CDC vs Metastability ⭐⭐⭐⭐⭐

Don't confuse these.

### CDC:

A **design situation/problem** where signals cross clock domains.

### Metastability:

A **physical behavior** that can occur when a receiving flip-flop samples data near its clock edge.

Relationship:

**CDC→Metastability Risk**

but:

**CDC itself is not metastability**
